# Data Warehouse Design

## 1. Overview

This document describes the first analytical data warehouse design for the FinPulse project.

The OLTP database is designed for transactional processing. It stores normalized operational data such as users, customers, accounts, cards, transactions, merchants, fees, fraud rules, and risk alerts.

The data warehouse layer is designed for analytical processing. It restructures OLTP data into dimensional tables and fact tables so that business users, analysts, and machine learning pipelines can answer analytical questions efficiently.

The proposed warehouse design follows a star schema approach.

---

## 2. OLTP vs Data Warehouse

| Aspect         | OLTP Layer                                              | Data Warehouse Layer                               |
| -------------- | ------------------------------------------------------- | -------------------------------------------------- |
| Main purpose   | Store daily operational transactions                    | Support analytics and reporting                    |
| Data model     | Normalized relational model                             | Dimensional model                                  |
| Query pattern  | Insert, update, lookup, transaction processing          | Aggregation, filtering, historical analysis        |
| Main users     | Application system, operations team                     | Data analysts, BI users, ML engineers              |
| Example tables | `txn.transactions`, `core.accounts`, `risk.risk_alerts` | `fact_transactions`, `dim_customer`, `dim_channel` |

---

## 3. Analytical Requirements

The data warehouse should support the following business questions:

1. How many transactions occur per day, month, channel, and transaction type?
2. What is the total transaction amount by customer segment?
3. Which channels generate the highest transaction volume?
4. Which merchant categories are associated with high-value or high-risk transactions?
5. How much fee revenue is generated by transaction type, channel, and currency?
6. Which transactions trigger risk alerts?
7. Which fraud rules generate the most alerts?
8. What is the average risk score by merchant category and channel?
9. How many alerts are open, reviewed, escalated, or dismissed?
10. Which customers or accounts have suspicious transaction behavior?

# 5. Dimension Table Design

## 5.1 DIM_DATE

```text
DIM_DATE (
    date_key,
    full_date,
    day_of_month,
    month_number,
    month_name,
    quarter_number,
    year_number,
    day_of_week,
    day_name,
    is_weekend
)
```

**PK:** `date_key`

**Grain:** One row per calendar date.

**Source:**

```text
Generated calendar table
```

**Purpose:**

The `DIM_DATE` table supports time-based reporting such as daily, monthly, quarterly, and yearly transaction analysis.

# 6. Fact Table Design

## 6.1 FACT_TRANSACTIONS

```text
FACT_TRANSACTIONS (
    transaction_key,
    transaction_id,
    transaction_date_key,
    customer_key,
    account_key,
    branch_key,
    currency_key,
    channel_key,
    transaction_type_key,
    merchant_key,
    transaction_amount,
    transaction_status,
    transaction_count,
    created_at
)
```

**PK:** `transaction_key`

**Grain:**

```text
One row per transaction.
```

**FK:**

```text
transaction_date_key → DIM_DATE(date_key)
customer_key → DIM_CUSTOMER(customer_key)
account_key → DIM_ACCOUNT(account_key)
branch_key → DIM_BRANCH(branch_key)
currency_key → DIM_CURRENCY(currency_key)
channel_key → DIM_CHANNEL(channel_key)
transaction_type_key → DIM_TRANSACTION_TYPE(transaction_type_key)
merchant_key → DIM_MERCHANT(merchant_key)
```

**Measures:**

```text
transaction_amount
transaction_count
```

**Source OLTP tables:**

```text
txn.transactions
core.accounts
core.customers
core.branches
ref.currencies
ref.channels
ref.transaction_types
ref.merchants
```

**Purpose:**

The `FACT_TRANSACTIONS` table is the central fact table of the warehouse.

It supports transaction volume, transaction amount, customer activity, channel performance, and merchant analysis.

# 10. Slowly Changing Dimension Strategy

Some dimension attributes may change over time.

## 10.1 SCD Type 1

Use SCD Type 1 when historical changes are not required.

Recommended for:

```text
dim_currency
dim_channel
dim_transaction_type
dim_merchant_category
dim_fraud_rule
dim_admin
```

## 10.2 SCD Type 2

Use SCD Type 2 when historical changes should be preserved.

Recommended for:

```text
dim_customer
dim_account
```

For SCD Type 2 dimensions, include:

```text
effective_from
effective_to
is_current
```

This allows the warehouse to keep customer and account history over time.

# 11. Suggested Implementation Order

The warehouse layer should be implemented in the following order:

```text
1. Create warehouse database and schemas
2. Create dimension tables
3. Create fact tables
4. Create date dimension seed script
5. Load dimensions from OLTP
6. Load fact tables from OLTP
7. Add warehouse validation queries
8. Add analytical queries for BI
```

Suggested SQL files:


# 13. Conclusion

The proposed FinPulse data warehouse design transforms normalized OLTP data into an analytical star schema.

The design separates descriptive dimensions from measurable facts, enabling efficient business intelligence, fraud monitoring, and future machine learning feature engineering.

This warehouse layer will become the foundation for the next project milestones: ETL/ELT pipeline development, BI reporting, fraud detection modeling, and MLOps integration.
